## חלק א — מפת ה-cluster

| רכיב | איפה הוא רץ (הנהלה / כל node) | מה הוא עושה, במשפט אחד | אנלוגיה |
|---|---|---|---|
| API server | הנהלה | נקודת הכניסה היחידה לאשכול: כל בקשה, מ-kubectl או מרכיב אחר, עוברת דרכו, והוא היחיד שמדבר עם etcd. | דלפק הקבלה: כל פנייה לבית החולים עוברת דרכו |
| etcd | הנהלה | מסד הנתונים ששומר את כל המצב של האשכול: אילו משאבים קיימים ומה ההגדרות שלהם. | ארכיון התיקים הרפואיים |
| scheduler | הנהלה | מחליט על איזה node ירוץ כל pod חדש, לפי המשאבים הפנויים והדרישות של ה-pod. | אחראי השיבוץ שמחליט באיזו מחלקה יאושפז כל מטופל |
| controller manager | הנהלה | בודק כל הזמן שהמצב בפועל תואם למצב הרצוי ומתקן פערים, למשל מקים pod חדש במקום אחד שנפל. | האחות הראשית שעוברת בסבבים ומוודאת שהכול כמו שצריך |
| kubelet | כל node | הסוכן שרץ על כל node, מקבל מההנהלה אילו pods צריכים לרוץ עליו, ודואג שהם באמת רצים ותקינים. | מנהל המחלקה שמקבל הוראות מההנהלה ודואג לביצוען במחלקה שלו |
| container runtime | כל node | התוכנה שמריצה בפועל את הקונטיינרים (אצלנו Docker), לפי ההוראות של ה-kubelet. | הצוות המטפל שעושה בפועל את העבודה בחדרים |
| kube-proxy | כל node | מנהל את כללי הרשת ב-node, כך שתעבורה שנשלחת ל-Service תגיע לאחד ה-pods שמאחוריו. | השילוט וההכוונה שמפנים כל מבקר לחדר הנכון |
| coredns | כל node (רץ כ-pod ב-kube-system) | שרת ה-DNS הפנימי של האשכול: מתרגם שמות של Services לכתובות IP, בדיוק כמו שב-Docker Compose (שיעור 4) קונטיינרים מצאו זה את זה לפי שם השירות. | המודיעין: "מחפשים את ד"ר כהן? שלוחה 34" |

## חלק ב — תרחישים

### 1. scale
1. kubectl שולח את הבקשה ל-**API server**, שבודק אותה ושומר ב-**etcd** שה-Deployment `web` צריך עכשיו 4 העתקים במקום 2.
2. ה-**controller manager** מזהה פער בין המצב הרצוי (4) למצב בפועל (2), ויוצר 2 אובייקטי pod חדשים. בשלב הזה הם במצב Pending, עדיין בלי node.
3. ה-**scheduler** רואה pods בלי node, ומשבץ כל אחד מהם ל-node עם מספיק משאבים פנויים.
4. ה-**kubelet** של ה-node שנבחר רואה שהוקצה לו pod חדש, ומורה ל-**container runtime** למשוך את האימג' (אם צריך) ולהפעיל את הקונטיינר.
5. ה-kubelet מדווח ל-API server שה-pod רץ, הסטטוס נשמר ב-etcd, ו-`kubectl get pods` מציג 4 pods במצב Running.

### 2. pod קרס בשלוש בלילה
כשהקונטיינר קורס, ה-**kubelet** שעל אותו node מזהה שהתהליך יצא ומפעיל אותו מחדש באותו pod. מספר ה-RESTARTS עולה, ואם הקריסות חוזרות, ההמתנה בין ניסיון לניסיון מתארכת (CrashLoopBackOff). אם מישהו מוחק את ה-pod כולו, ה-**controller manager** מזהה שנשארו פחות pods ממה שה-Deployment דורש, ויוצר pod חדש עם שם וכתובת IP חדשים. ה-scheduler משבץ אותו וה-kubelet מפעיל אותו. בשני המקרים אף אדם לא צריך להתעורר.

### 3. node נכבה
בכיתה יש node אחד, והוא גם ההנהלה וגם המקום שבו רצים ה-pods. לכן אם המחשב נכבה, כל ה-cluster נעצר ואין מי שיתקן. כשהמחשב עולה מחדש, Docker Desktop מפעיל את ה-cluster והכול חוזר לרוץ. בענן עם 3 nodes, ההנהלה מפסיקה לקבל "דופק" מ-node 2 ומסמנת אותו NotReady. אחרי זמן המתנה (כמה דקות), ה-pods שהיו עליו מסומנים לפינוי, ה-**controller manager** יוצר pods חלופיים, וה-**scheduler** משבץ אותם על שני ה-nodes שנשארו. pods שנוצרו בלי Deployment פשוט אובדים.

### 4. מעבר ל-EKS
`imagePullPolicy: Never` אומר ל-kubelet לא למשוך אף פעם את האימג', ולהשתמש רק במה שכבר קיים על ה-node. בכיתה זה עבד כי בנינו את האימג'ים על אותו מחשב. ב-EKS ל-nodes אין את האימג'ים, וה-pods ייתקעו ב-`ErrImageNeverPull`. צריך לדחוף את האימג'ים ל-registry (למשל ECR או Docker Hub), לעדכן את שדה `image` לכתובת המלאה עם tag, ולשנות ל-`IfNotPresent` או `Always`. בנוסף, `NodePort` פותח פורט גבוה (30000–32767) על כתובת ה-IP של כל node. בענן הכתובות האלה פרטיות או משתנות, ולכן זה לא מתאים לחשיפה ללקוחות. במקומו משתמשים ב-Service מסוג `LoadBalancer` (שיוצר Load Balancer של AWS) או ב-Ingress.

### 5. pod בודד
pod שנוצר ב-`kubectl run` הוא pod "יתום": אין שום controller שאחראי עליו. כשמוחקים אותו, אף אחד לא שם לב שהוא חסר ולא יוצר אותו מחדש. ה-pod של `web` חזר כי הוא שייך ל-Deployment, וה-**controller manager** דואג תמיד שמספר ה-pods יתאים למה שהוגדר בו. כדי ש-stats יחזור תמיד, צריך ליצור אותו כ-Deployment, כמו בקובץ `stats-deployment.yml`, ולהחיל אותו עם `kubectl apply -f`.
